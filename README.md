# rail-tiles

Turns OSM extracts into a PMTiles railway pyramid (z2–z16) served over HTTP range
requests. Built weekly by GitHub Actions and published to Releases as
**per-continent archives**; a `manifest.json` at the stable `latest` tag lists
each archive with its bounds. Each build also ships a per-tile change list, so a
client updates by refetching only the tiles that changed rather than purging its
cache (see [Incremental updates](#incremental-updates)).

## What's here

| path | role |
|---|---|
| `pipeline/regions.json` | the worldwide build matrix (generated by `gen_regions.py` from Geofabrik's index, which warns when one region lies inside another and would be built twice) |
| `pipeline/` | classify tags → typed fields, chain ways, collapse parallel track, tile per zoom, verify |
| `pipeline/partition.py` | keep each border way in exactly one region |
| `pipeline/border_check.py` | check across regions that no border way was lost |
| `pipeline/join_planet.py` | group region tilesets by continent, merge and tile the stations, tile-join each |
| `pipeline/zstd_tiles.py` | rewrite a joined archive with zstd tiles |
| `pipeline/diff_tiles.py` | per-tile content hashes and the change list between two builds |
| `pipeline/stations.py` | station points and the services that call at each |
| `pipeline/train_protection.json` | which tags name a train protection system and which system wins on shared track (generated by `gen_protection.py` from taginfo counts) |
| `pipeline/night.py` | decide the night trains across regions and write their list |
| `pipeline/graph.py` | the track graph the app finds a trip's path on, per region |
| `pipeline/graph_join.py` | merge the regions' track graphs into chunks and a station file |
| `pipeline/manifest.py` | emit `manifest.json` (archives, bounds, `builds` chain, night-train list, track graph) |
| `scripts/fetch_region.sh` | download an extract (Geofabrik → OSM-France fallback), filter to railway ways |
| `.github/workflows/build-tiles.yml` | per-region matrix build → per-continent join → change lists → publish |
| `samples/` | a couple of pre-filtered extracts for local testing (switzerland, kenya) |

## Output

- Tiles are MVT, each compressed as one zstd level-19 frame with no
  dictionary (PMTiles `tile_compression` 4). Directories and metadata stay
  gzip. tippecanoe and tile-join write only gzip, so the join rewrites each
  continent archive afterwards (`zstd_tiles.py`); region archives stay gzip.
  zstd is about 4% smaller than gzip on these tiles. Manifest schema 4 marks
  the switch.
- z2–z16 `rail` layer. Below z12: merged chains carrying source spans.
  z12 and up: raw OSM ways.
- z9–z14 `stations` layer (schema 3): one point per station, see
  [Stations](#stations).
- Attributes (raw numbers; speed bands are the client's job): `kind`,
  `lifecycle`, `usage`, `service`, `elec`, `voltage`, `frequency`,
  `elec_proposed`, `proposed_voltage`, `proposed_frequency`,
  `maxspeed_construction`, `maxspeed_proposed`, `gauge_construction`,
  `gauge_proposed`, `tp_construction`, `tp_proposed`, `tp_change_rank`,
  `gauge_class`, `gauge_mm`, `gauge_mm_list`, `maxspeed`, `train_protection`, `tp_rank`,
  `radio`, `traffic_mode`, `colour`, `tunnel`, `bridge`, `name`, `ref`, `osm_id`, `src`,
  `absorbed` (ways a parallel collapse deleted beside this track, `w1;w2`).
- Service track (`service=*`) appears from z12, except where a route runs over
  it, such as a passing loop tagged as a siding. That track is in every zoom.
  The app draws a highlighted route from the ways in the tiles, so it would
  otherwise show a gap there below z12. Such track keeps its `service` tag and
  never merges with the line beside it.
- `kind` includes funicular; `lifecycle` includes preserved and razed.
  Construction and proposed lines read their prefixed tags
  (`construction:electrified`, `proposed:maxspeed`, ...) so they carry planned
  attributes. `maxspeed` handles mph and `maxspeed:forward`/`:backward`.
- `voltage` and `frequency` are the system being put up while
  `elec=construction`. `elec_proposed` marks a line in service with no wire
  yet and a `proposed:electrified` tag; `proposed_voltage` and
  `proposed_frequency` are its planned system.
- On a line in service, `maxspeed_*`, `gauge_*` and `tp_*` with the suffix
  `construction` or `proposed` are a change under way or planned: the value
  tagged under that prefix, when it differs from the current one.
  `construction:` wins over `proposed:`. `tp_change_rank` ranks the new
  system like `tp_rank`.
- `colour` is the OSM `colour` tag as a 24-bit RGB integer (`0xE4013A`). Hex in
  any case, `#rgb` and CSS names are normalised; values that do not parse are
  dropped. An integer is smaller in the tile than a `#rrggbb` string.
- `train_protection` is the one system a way shows when it is tagged with
  several. Systems built to run on top of a line's existing signalling while
  it migrates (ETCS, CTCS-2/3, KTCS, the North American PTC systems, CBTC) win;
  otherwise the system tagged on fewer ways worldwide wins, since on shared
  track the rarer one is the addition (LZB on PZB lines, TVM on KVB lines).
  `tp_rank` is that order, higher on top; `none` (every protection key says no)
  is 1. `gen_protection.py` holds the tag rules and states the method.
- `train_protection` (with `tp_rank`), `radio`, `traffic_mode` and `colour` are
  exact per way from z12 up and the dominant value over a merged line below; `tunnel` and
  `bridge` are exact per way from z12 up and "line contains one" below. So those
  views work at every zoom, sharpening from line-level to segment-level as you
  zoom in.
- Nothing is dropped by density — tippecanoe's drop flags stay off; density is
  managed by chaining (z2–z11) and segment-level parallel collapse (z2–z14).
- **8 continent archives, ~3.6 GB total** (a single planet file exceeds the 2 GB
  per-asset limit). A client loads only the archives overlapping the viewport and
  only the tiles it views.

## Stations

The `stations` layer holds a point per `railway=station`, `railway=halt` or
`railway=tram_stop` node, or `public_transport=station` for a rail mode. A
station mapped only as an area becomes its centroid. Main-line stations appear
from z9; halts and metro, light rail, monorail and funicular stations from z12;
tram stops from z13. The layer stops at z14, which places a station to about a
metre; the app draws deeper zooms from the z14 points, which saves ~40% of the
layer. On Switzerland, Madrid and Galicia it adds 4.3%, 3.3% and 1.8% to the
region archive.

| attribute | value |
|---|---|
| `osm_id` | `n<id>` (`w<id>` for an area) |
| `name` | the `name` tag |
| `kind` | `train`, `subway`, `light_rail`, `monorail`, `funicular`, `tram` |
| `halt` | true for `railway=halt` |
| `routes` | JSON `[[route, title, colour, network, [relation ids]], ...]` |

`routes` lists the services that call at the station. A route relation calls
there when one of its `stop*` or `platform*` members is in a
`public_transport=stop_area` that holds the station, or is the station. A stop
no stop area places counts for the nearest station of a matching mode within
250 m. A stop area holding a train and a metro station gives each only the
routes of its own mode. Relations group into one service by route type, network
and ref (or name), which is how the app's detail sheet groups them, so both
directions of a line are one entry. `colour` is the 24-bit RGB integer of the
first relation with a colour tag, or null.

Each region build writes its stations to `<region>.stations.geojsonseq` rather
than its own tiles. The join merges them by station across all regions, since
Geofabrik extracts overlap at borders and each holds only its own routes, so a
border station such as Basel SBB lists the services of both regions. The merged
layer is tiled once per continent that holds the station and joined beside its
rail layer. A local build without `--stations` tiles the layer into the region
archive instead.

The tiles carry only relation ids. The app fetches a service's member ways and
stops from the OSM API when the user opens it.

## Border partition

Geofabrik extracts overlap at borders. Each region keeps a border way only if
no region earlier in name order holds it, judged by that region's boundary
containing one of the way's nodes by more than 10 m (`pipeline/partition.py`,
boundaries in `pipeline/region_shapes.json`, written by `gen_regions.py
--shapes`). Every way is then built once instead of twice in the overlap. Each
region records the border ways it left and kept (`--border`), and the join's
`border_check.py` warns about any way left to a neighbour that the neighbour
did not keep. A local build without `--partition` keeps all ways.

## Night trains

Each build publishes `night-trains-<tag>.json.gz` beside the archives, and the
manifest names it under `nightTrains`. It lists the `route=train` relations
that count as night trains: those with `sleeping_car=yes` or `couchette=yes`
at any length, and those whose `service` includes `night` when the route is at
least 300 km long. The length check keeps out local trains that run at night,
such as NS Nachtnet. Each entry has the relation's tags, member ways, stop
nodes and length in km, and `service`: the id of the `route_master=train`
relation that lists it. `services` gives each of those route masters' tags. A
service groups a train's directions and branches; a train no route master
lists has no `service` and stands alone.

The tiles do not change. The app matches the member ways against the `osm_id`,
`src` and `absorbed` ways the tiles already carry.

Night trains cross borders, so no region can measure one alone. Each region
build writes `<region>.night.json` with its candidate relations and the length
of every member way it holds, and the join job decides from all of them.
Geofabrik extracts overlap at borders, so way lengths are united by way id
rather than summed per region. A region restored from a cache older than the
sidecars contributes nothing until it rebuilds, and the join warns about it.

## Track graph

The app finds the path of a trip between two stations on a graph of the
track (`pipeline/graph.py` states the format and the search's needs). Each
build publishes it beside the map archives, and the manifest names it under
`trackGraph` and `trackStations`, apart from `archives`, since it is not a
map:

| asset | contents |
|---|---|
| `track-graph-<tag>.rltg.pmtiles` | PMTiles, tile type 0, one zoom (`trackGraph.zoom`, 8): each tile a zstd frame of `graph.py`'s graph file with every edge that has an end in the tile |
| `track-stations-<tag>.rlts.zst` | `graph.py`'s station file: every train and light rail station with its name and its names in other languages, position, services and stop positions as node ids |

The graph holds only what a search needs: track a train can use, junctions
where a train can turn off or stop, edges listing the ways they cover, and
outlines within 5 m of the track for drawing a trip. Germany takes 5.9 MB
in 55 chunks.

The app searches stations by name in the station file, then loads the chunks
along a trip: the chunk a junction lies in holds every edge at that
junction, since an edge between two chunks is in both. It joins chunks by OSM
node id and drops an edge identical to one it already has.

Each region builds its graph from its whole extract into
`<region>.graph.jsonl.zst`, border ways included: the border partition would
leave a way to one region while only the other region's extract holds the
branch that meets it. The join gathers every region's copy of a way and
cuts its newest OSM version wherever any copy has a cut, by node id, so the
branch finds a junction there even when the neighbour was carried forward
with an older version of the way. Station names, positions and services
are the map's, from the same station sidecars and merge as the stations
layer; the graphs add the stop positions. A Germany-only join gives the same
edges as `graph.py` on the extract, and the app's search costs on it what
`search.py` costs on the unmerged graph; Germany, Austria, Switzerland,
Liechtenstein and Italy together find paths across every border between
them.

The graph caches per region apart from the tiles, so a change to one
rebuilds only that one.

## Build

Weekly cron plus manual dispatch. 242 regions worldwide (country level; the US as
states; Canada and Russia whole; cross-border aggregates excluded). Per region:
fetch → filter → tile → verify, skipping regions whose extract is unchanged
(md5-keyed cache). Then `join_planet.py` tile-joins per continent into
`<continent>-<date>.pmtiles`, all published to a dated Release, and the manifest
at `latest` lists them with bounds. A smoke run (dispatch with a `regions` list)
builds an artifact and does not publish. A test run (dispatch with a
`test_tag`) builds the whole world and publishes it as a prerelease under that
tag, with its own `manifest.json`; it leaves `latest` and the prune alone, and
its release stays until deleted by hand. The build tolerates a region failing:
`fail-fast: false` and the join runs on partial success.

## Incremental updates

A weekly rebuild changes well under 1% of tiles (rail geometry barely moves), yet
a new `buildId` would otherwise make the client purge its whole cache. So each
build also emits, per continent, the exact set of tiles that differ from the
previous build:

| asset | audience | contents |
|---|---|---|
| `<continent>-<tag>.hashes` | build-internal | tileId → 8-byte content hash for every tile. Binary, ~3 MB (Australia) to ~27 MB (Europe). |
| `<continent>-<tag>.changed` | client | gzipped JSON `{from, to, region, counts, tiles:[[z,x,y]…]}`. A few KB up to ~40 KB (Europe). |

`diff_tiles.py` hashes each joined archive's decompressed tiles, so neither
the codec nor the zstd version changes a hash, and compares against the previous
build's `.hashes` (downloaded from the prior release, never the multi-GB
archive). The manifest gains `tag`, `baseUrl`, and `builds` (recent dated tags,
oldest→newest, the last 26 builds). A client finds its last-seen tag in
`builds`, fetches each later tag's `.changed`, and marks only those tiles stale;
a client older than `builds[0]`, or one that 404s a `.changed`, marks the whole
continent stale and refetches it lazily. The window is half a year at weekly
cadence because the app ships a low-zoom seed stamped with a build tag and
chains it forward from there, so it has to stay inside the window for the life
of an app release. The first build after this shipped has no prior `.hashes`, so
it publishes hashes only; change lists begin one build later. The same holds for
the first zstd build. The hashes before it covered the stored gzip bytes, so
`diff_tiles.py` refuses to compare them, and the schema bump has the app start
fresh anyway.

Releases are permanent: GitHub keeps a release and its assets until deleted, so
old `.changed` stay fetchable and the chain is only bounded by the `builds` cap.
The per-region tilesets are Actions **artifacts** (`retention-days: 3`) and do
expire. After a full build publishes, a prune step deletes `.pmtiles` older than
14 days and `.hashes` from all but the 2 newest releases, and keeps the change
lists. [RETENTION.md](RETENTION.md) gives the reasoning.

## Local

```
make selftest              # merge-honesty gate, no data
make build R=switzerland   # build one sample region
make verify R=switzerland  # run the gates on it
make join                  # tile-join the sample builds
```

Needs `osmium`, `tippecanoe`, `tile-join`, `tippecanoe-decode`, Python 3.14+
(for `compression.zstd`).
Regenerate the region matrix with
`python3 pipeline/gen_regions.py index-v1.json > pipeline/regions.json`, and
the train protection table with
`python3 pipeline/gen_protection.py pipeline/train_protection.json`. It
replaces the table only when the run succeeds and a rank, tag or key changed,
since the region cache key hashes the table. It keeps the previous order
unless a system's tagging moved by more than a quarter.

## Gates

Feature conservation, category presence at low zoom, per-tile vertex budget,
attribute completeness, merge honesty, connectivity (collapse must not sever
lines).
